## Verified facts (README as summarised)
1. Purpose: "Display Fire Data from Around the World using NASA's Fire Information for Resource Management System (FIRMS) API."
2. Architecture (Docker Compose): FastAPI app serves map and API; Postgres stores history; Valkey holds only the current snapshot, which "expires right around the time the next reload is due"; a small scheduler loop calls `/reload` each interval.
3. Ingest: FIRMS `area` API with `world` as bounding box, "not per country". README says the API "dropped country attribution" after NASA retired the country-based endpoint (claim about the FIRMS Area API `country` endpoint; REPO CLAIM, needs R2 to confirm on FIRMS pages; it concerns the API, not necessarily the archive country CSV downloads we use).
4. History: every reload appends detections to `fire_detections` ("a full timeline of everything FIRMS has ever reported"); `GET /history` filter by `since` / `scan_id`; `GET /scans` lists scans with counts.
5. Rate limits: README does not mention FIRMS rate limits or MAP_KEY (says to fill `NASA_API_KEY`). So it gives no rate-limit lesson; caching via snapshot + scheduler means one world request per interval, independent of number of viewers.
6. Licence: none stated in README or repo page (treat as all rights reserved; do not copy code). Python 3.14, mise, uv.
7. Frontend/tiling: not described.

## Lessons for a static PWA
- Pattern: one scheduled fetch -> store -> clients read the stored snapshot. Our equivalent: a scheduled/offline build writes static JSON; clients never call FIRMS (no key in browser). This is already our design.
- Server + DB is exactly what we avoid; do not adopt.
