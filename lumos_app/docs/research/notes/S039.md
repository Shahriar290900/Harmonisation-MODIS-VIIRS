# S039 IGNIS (Hisernberg/ignis-public) README
Fetched 2026-10-10 by R4 via WebFetch (HTTP 200; content is a model-written summary of the README with quotes, not raw HTML). Describe-only note: the pack says do not copy code, wording, UI, datasets or claimed results.

## What it is
A same-challenge (NASA Space Apps 2026, Challenge #9) public submission: a 26-year burning-activity calendar "2000 to today" plus cluster segmentation, anomaly/trend tools, fire-weather fusion and an LLM "AI analyst". README calls it a sanitized public mirror of a keyed deployment. Licence MIT; says "Not endorsed by NASA".

## Verified facts (as stated in the README)
1. Stack: Next.js 16 + TypeScript + Tailwind + MapLibre GL, on Vercel with API routes. Needs `FIRMS_MAP_KEY` and an Earthdata bearer token (`EDL_TOKEN`) at runtime. This is a live server app, not a static one.
2. Data: FIRMS Area API (5 sensors) as primary live feed; NASA GIBS vector tiles (MVT archive back to Nov 2000) as fallback "where FIRMS is blocked"; EONET v3; Open-Meteo; LP DAAC MOD11 LST; Hugging Face models/datasets at runtime.
3. Calibration method: r(m) = median(VIIRS-SNPP / MODIS) per month m over the 2012+ overlap; pre-2012 est(m) = MODIS(m) x r-bar; CV of the ratio shown as the uncertainty readout; rows flagged `scaled: true`. README gives no accuracy figure for the harmonization itself ("No formal accuracy figures are given for the harmonization itself beyond the CV readout").
4. Clustering: grid-accelerated DBSCAN, eps = clamp(span/45 deg, 0.14, 0.9 deg), minPts = 3; convex hulls; persistence tracked by nearest centroid across a 7-day replay.
5. Anomaly: |z| >= 2 flags, STL-style decomposition, CUSUM, Theil-Sen trend, harmonic regression forecast.
6. Precomputed monthly calendars for 9 regions plus Bangladesh in `data/ignis/`, built by `build_calendar.mjs` from the GIBS archive.
7. Rate limits: `NASA_API_KEY` defaults to `DEMO_KEY` ("rate-limited"); without a MAP_KEY the app falls back to GIBS. README describes no retry/backoff code.
8. Claimed model numbers (README quotes, NOT reproducible by us, labels derived from their own segmentation = weak labels): regime model "63 complexes, silhouette 0.178, 4 megafires"; classifier "HGB ref 0.763, extra-trees portable twin 0.685 held-out agreement"; event detector "AUC 0.740, PR-AUC 0.606 on 2022-26 holdout"; footprint forecaster "IoU 0.58/0.55/0.42 vs persistence 0.36/0.39/0.38". Uses the phrase "honest holdout" without methodology.

## Caveats
- Summary came through a fetch-summariser; exact wording in the quotes above should be re-checked on the page before any citation.
- Their "continuity ratio" treats S-NPP/MODIS as one ratio per month, same family as the pack's baseline. Nothing in the README shows overlap-period holdout of that ratio.

## Where we differ (for R5)
- Ours: static PWA, no server, no keys at runtime; 5 km Lambert CEA grid x UTC month; Aqua->S-NPP backcast (2003-2012); Poisson GLM + ratio baselines; 80% prediction intervals; temporal and spatial-block holdout; release stages. Theirs: server-side Next.js app with live APIs, AOI-level (not gridded) monthly ratio from median of ratios, CV as uncertainty, plus LLM analyst.
- Do not echo: any AUC/IoU/silhouette numbers, "validated", "honest holdout", "26-year" (ours is 2001-2025), "2000 to today", or their screen set. Their classification labels are weak labels from their own algorithm, so those scores are not evidence of fire detection accuracy.
- Ideas worth noting independently (generic, not copying): GIBS as a keyless fallback; health status rail for upstream sources; "scaled" flag per row (we already have observed/calibrated/mixed provenance).
